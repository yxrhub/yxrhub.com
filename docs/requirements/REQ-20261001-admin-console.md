## 1. 背景与动机

站点已具备完整的 GitHub OAuth 登录闭环（`better-auth` + Drizzle/PostgreSQL），但**整个项目没有任何管理能力**：

- `user` 表里没有 `role` 字段，也没有任何管理员概念；
- 全站只有两个路由：`/`（首页）与 `/api/auth/[...all]`（认证）；无后台；
- 要查看或修改用户信息，只能直接连数据库操作。

当前生产库（`yxrhub` @ `192.168.0.80:5433`）已有真实数据：`user` 1 行、`session` 3 行。数据虽少，但"只能手改数据库"是不可持续的——任何一次用户维护都要求直接操作生产库，风险高且无法审计。

## 2. 目标

提供一个仅管理员可访问的 `/admin` 后台界面，使日常的用户信息维护（查看、编辑、封禁、角色调整、会话处置）**全部在界面上完成**，不再需要直接接触数据库。

## 3. 范围

### 3.1 本次要做(In Scope)

**基础资料**
- [ ] 用户列表：分页浏览，支持按 `email` / `name` / `username` 搜索
- [ ] 用户详情：基本信息 + 关联的登录方式（account provider）+ 会话概况
- [ ] 编辑基本资料：`name`、`username`、`displayUsername`、`email`、`emailVerified`

**账号状态**
- [ ] 角色变更：`user` / `admin`
- [ ] 封禁 / 解封：可填写封禁原因与可选到期时间；**封禁时同步吊销该用户全部现有会话**
- [ ] 删除用户（`session` / `account` 经外键级联一并删除）

**会话**
- [ ] 查看某用户的全部会话：IP、User-Agent、创建时间、到期时间
- [ ] 吊销单个会话 / 吊销全部会话

**账号操作**
- [ ] 模拟登录（impersonate）指定用户，并可退出模拟；模拟期间界面常驻提示
- [ ] 为指定用户设置密码
- [ ] 新建用户：`email` + `name` + 可选密码 + 角色

### 3.2 本次明确不做(Out of Scope)

- **权限分级**：只区分 `admin` / `user` 两级，不做更细的角色与权限矩阵（`better-auth` 的 access control 能力本次不展开）
- **操作审计**：不建审计表、不记录"谁在何时改了谁"
- **邮件能力**：忘记密码、邮件验证、任何通知邮件
- **用户自助**：注册页、个人资料页、账号设置页
- **头像上传 / 文件存储**
- **批量操作**：批量封禁、批量删除、批量导出
- **数据导出**（CSV / JSON）
- **多租户 / 组织（organization）**

## 4. 验收标准

**访问控制（最高优先级）**

- [ ] 未登录用户访问 `/admin`，返回 **404**，响应中不含任何后台相关内容
- [ ] 已登录但 `role` 不含 `admin` 的用户访问 `/admin`，同样返回 **404**
- [ ] 非管理员直接 `curl /api/auth/admin/list-users`，返回 **403**；未登录返回 **401**
  —— 即权限校验发生在**服务端**，而不是仅隐藏前端入口
- [ ] 前端界面上，非管理员看不到任何后台入口

**基础资料**

- [ ] 管理员可在列表中按 `email` / `name` / `username` 搜索，并翻页浏览
- [ ] 修改 `name` / `username` / `displayUsername` / `email` / `emailVerified` 后，重新加载页面可见新值

**账号状态**

- [ ] 变更角色后，目标用户下次登录获得对应权限
- [ ] 被封禁用户**立即**无法登录，且其封禁前已存在的会话已被吊销
- [ ] 解封后该用户可正常登录
- [ ] 删除用户后，该用户对应的 `session` / `account` 记录不复存在（外键级联）

**会话与账号操作**

- [ ] 可查看指定用户的会话列表，并能吊销单个或全部会话
- [ ] 可模拟登录指定用户，界面出现明确的"正在以 X 身份浏览"提示，且可一键退出模拟
- [ ] 可为指定用户设置密码
- [ ] 可新建用户并指定角色

**安全护栏**

- [ ] 管理员**无法**封禁自己、删除自己、把降级自己（UI 禁用 + 服务端拒绝）
- [ ] 删除、封禁、降级角色、模拟登录等危险操作，均需二次确认

## 5. 约束与依赖

| 类型 | 说明 |
| --- | --- |
| 技术约束 | 必须启用 `better-auth` 的 `admin` 插件，这要求给 `user` / `session` 表新增字段。管理接口由插件提供（`/api/auth/admin/*`），服务端通过 `hasPermission({ role })` 强制校验，默认管理员角色为 `admin` |
| 技术约束 | **数据库同步使用 `drizzle-kit push`，不产生迁移文件。** 本项目处于开发期、表结构变动频繁，**刻意不使用迁移机制**（仓库无 `drizzle/` 目录，库中无 `__drizzle_migrations`），且当前连接的是**开发库**（非生产）。这是既有约定，不是本次引入的权宜之计 |
| 技术约束 | 不可触碰既有红线：`schema/auth.ts` 既有字段名、`middleware.ts` 的 `isPrerendered` 短路、`astro.config.mjs` 的 `ssr.noExternal` |
| 兼容性 | 新增字段全部可空或带默认值，属**加列**操作，不破坏现有数据与登录会话；现有 1 个用户的 `role` 为 `NULL`，`better-auth` 会按 `defaultRole`（`user`）处理，即自动视为普通用户 |
| 数据风险 | 目标为**开发库**（`user` 1 行 / `session` 3 行），经确认无需备份。**但走向生产库前必须重新评估迁移策略**——对生产库直接 `push` 会在无版本记录、无回滚路径的情况下改动结构 |
| 外部依赖 | 无需新增密钥或第三方账号 |

## 6. 待确认问题（已全部确认）

- [x] **迁移策略** → 采用 `drizzle-kit push`。本项目开发期表结构变动频繁，**刻意不使用迁移文件**；当前连接的是开发库。
- [x] **迁移前备份** → 不需要（开发库）。

- [x] **首个管理员** → 使用当前唯一用户（`h***@yxrhub.com`，GitHub 登录），手工执行 SQL 提升。

## 7. 补充说明

- 已确认 `better-auth@1.6.20` 自带 `admin` 插件，提供 15 个端点：`list-users`、`get-user`、`create-user`、`update-user`、`remove-user`、`set-role`、`ban-user`、`unban-user`、`set-user-password`、`list-user-sessions`、`revoke-user-session`、`revoke-user-sessions`、`impersonate-user`、`stop-impersonating`、`has-permission`。
- 插件新增字段：`user.role`、`user.banned`、`user.banReason`、`user.banExpires`、`session.impersonatedBy`。
- **已知行为（易踩坑）**：插件只在 `session.create` 时检查 `banned`，因此封禁一个**已登录**用户不会立刻使其现有会话失效——这正是验收标准中要求"封禁同时吊销会话"的原因。
- 界面沿用现有设计令牌（`Layout.astro` 的明/暗两套 CSS 变量）与 React 岛屿水合方式。
