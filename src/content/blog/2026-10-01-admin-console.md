到现在为止，这个站有一个完整的登录系统，但**没有任何管理能力**。

想看一眼用户列表、修个用户名、封掉一个异常账号，都只能直接连数据库。数据量小的时候这不算事，但"只能手改数据库"意味着每次用户维护都是一次高风险操作——没有界面、没有确认、没有留痕。

所以有了 `/admin`。这篇记录围绕它做的几个判断，以及一个三个月前埋下的坑如何准时回来收账。

## 一、不自己写管理 API

第一种思路是自建：写几个 `/api/admin/*` 路由，查库、改库、在路由开头加一句"判断当前用户是不是管理员"。

**这个思路的问题在于，它把最容易出错的那部分留给了自己**。权限校验看起来是一行 `if`，实际上它要同时保证三件事：

- 请求确实带着**有效会话**（不是伪造的 cookie）；
- 该会话对应的用户**当前**是管理员（角色可能刚被改过）；
- 校验发生在**服务端**，不是只隐藏了前端按钮。

better-auth 的 `admin` 插件把这三件事连同 15 个端点一起提供了：`list-users`、`create-user`、`update-user`、`remove-user`、`set-role`、`ban-user`、`unban-user`、`set-user-password`、`list-user-sessions`、`revoke-user-session`、`revoke-user-sessions`、`impersonate-user`、`stop-impersonating`、`has-permission`、`get-user`。

权限由插件内部强制（有会话 + `hasPermission({ role })`），前端只是调用方。**自己重写一遍的意义只有"可控"，代价是把最不该出错的一层变成了自研代码。**

## 二、角色判断里的一个隐蔽陷阱

需求只区分 `admin` 和 `user` 两级，所以判断"是不是管理员"看起来就是一次字符串比较。

但 `role` 字段支持**逗号分隔的多值**（比如 `admin,editor`）。于是这个非常自然的写法是错的：

```ts
// ❌ superadmin 会被误判为管理员
const isAdmin = (user) => user?.role?.includes("admin");
```

`"superadmin".includes("admin")` 返回 `true`。同样地，`"not-admin"` 也会被判成管理员。

正确写法是按分隔符切开再精确匹配：

```ts
// src/lib/authz.ts
export function isAdmin(user) {
  if (!user?.role) return false;
  return user.role.split(",").some((r) => r.trim() === "admin");
}
```

**这个 bug 的特殊之处在于它现在不会发作。** 当前只有 `admin` / `user` 两个值，两种写法结果完全一样。它是一颗定时炸弹——哪天出现一个包含 `admin` 字样的新角色，判断就悄悄错了，而且错的方向是**放行**（把非管理员当管理员），是最危险的方向。

所以它被写进了红线：**角色判定必须按分隔后精确匹配。**

## 三、三个月前那行「顺手加的」代码回来收账

后台的第一个功能是"管理员登录后在导航里看到『管理』入口"。

实现很直接——在 `Header.astro` 里按登录态条件渲染：

```astro
{isAdmin(Astro.locals.user) && <a href="/admin">管理</a>}
```

**结果是：管理员登录后也看不到这个入口。** 手动敲 `/admin` 却能正常进入。

原因要回到三个月前写中间件时那行"顺手加的"代码：

```ts
// 中间件
if (context.isPrerendered) return next();   // ← 就是这一行
const session = await auth.api.getSession({ headers: context.request.headers });
context.locals.user = session?.user ?? null;
```

当时加它的理由很正当：静态页面读 `Astro.request.headers` 会触发警告，而且语义上没有意义。

但它带来一个当时没意识到的后果：**首页是预渲染的静态页，因此走的是这个提前返回，`Astro.locals.user` 恒为 `null`。** 于是上面那段条件渲染永远是 `false`——它是一段死代码。

**兜了一圈，问题回到了那篇身份层日志里挖的坑：预渲染页拿不到 `locals.user`。**

修法是把入口**下沉到客户端岛屿**——放进 `LoginButton`，用 `authClient.getSession()` 拿到的 `session.user.role` 判断。登录态本来就是在客户端解析的，这个位置的判断才成立。

顺带把两个层面的职责分清了：

- **前端入口**只是便利，不构成防护；
- **真正的访问控制在中间件**，非管理员与未登录一律返回 **404**（而不是 403——403 等于告诉对方"这里存在一个你不能进的页面"）。

这两条也写成了红线：**需要登录态的页面必须 `export const prerender = false`；不要在预渲染页里用 `locals.user` 做条件渲染。**

## 四、封禁：一个假设错了，一个假设对了

计划里把"封禁不立即生效"列为高危风险，依据是：**better-auth 只在创建会话时检查 `banned` 字段**，所以封掉一个已经登录的用户，他手上的会话依然有效。

这个判断是**对的**——如果只调用 `ban-user`，用户的现有会话确实不会被吊销。

但接下来发现，**计划里给出的应对是多余的**：`ban-user` 的实现内部自己就会吊销该用户的全部会话。

于是原计划里"封禁流程需要额外调用 `revoke-user-sessions`"这一步被删掉了。多写一次不会出错，但**会让代码表达一个不存在的需求**——后来的维护者会以为这个调用是必需的，进而以为插件不会处理会话，进而对整个行为建立错误的模型。

## 五、模拟登录的两个推论

「模拟登录」（impersonate）允许管理员以某个用户的身份浏览站点，用于复现用户看到的问题。它带来两个不那么直观的后果。

**推论一：模拟期间访问 `/admin` 必然 404。**

因为此刻的身份是**被模拟的那个普通用户**，中间件判定他不是管理员，直接返回 404。

这不是 bug，是权限模型自洽的结果——模拟的意义就是"以他的权限看世界"，如果模拟期间还能进后台，那权限判断反而有问题了。

**推论二：那个 404 页面是光秃秃的。**

因为它是中间件直接返回的裸 HTML，**不经过 Layout**。也就是说，模拟期间一旦进入 `/admin`，站点外壳（导航、页脚）全部消失，只剩一行 404 文字——连个能点的地方都没有。

这两条推到一起，得到一个设计结论：**"正在以 X 身份浏览 / 退出模拟"的提示条必须挂在全局 Layout 上，而不是后台页面里。** 否则一旦进入某些页面，用户就失去了退出的入口。

所以模拟成功后整页跳回首页，提示条固定悬浮在底部——它必须在**任何**页面都能看到和操作。

## 六、怎么验证一个有登录保护的后台

这是这次最花心思的部分。

后台的行为（权限判断、封禁、模拟登录）**全都依赖真实登录**，而本地开发环境没法用浏览器手工登录（GitHub OAuth 回调指向的是线上域名）。

第一反应是"那就拿数据库里的会话 token 当 cookie 发请求"。**这个思路不成立**。会话 cookie 的值经过 HMAC-SHA256 签名，密钥是 `BETTER_AUTH_SECRET`；把库里的原始 token 直接当 cookie 用，请求会返回 200，但 `user` 字段是空的——**它看起来成功了，实际什么都没验证到**，这种"看似通过"的验证比不做验证更危险。

可行的做法是两条腿：

1. **在本地库里插一条带标记的会话**（用自己的库、自己的库表）；
2. **按 `BETTER_AUTH_SECRET` 算出合法签名**，拼出 cookie；然后用无头 Chrome 通过 CDP 驱动真实点击。

这样跑下来，覆盖了：新建用户 → 编辑资料 → 封禁（验证会话数归零）→ 解封 → 设置密码 → 模拟登录 → 退出模拟 → 删除（验证未输入目标邮箱时按钮禁用）。

**收获确认了两件事**：一是主流程全通、控制台无错误；二是上面第五节那两个推论——如果不是真的走了一遍模拟登录，我不会发现"提示条挂错位置就再也退不出来"。

有一条纪律是同步定下的：**验证用的会话在结束后立即删除，并核对数据恢复原状。** 验证手段本身不能改变被验证的环境。

## 七、文档里的错误会传播

这次还纠正了一个更早的错误。

`AGENTS.md` 里原本写着"数据库变更只能走 `drizzle-kit generate`"。实际情况正相反：这个项目**刻意不用迁移文件**——仓库里没有 `drizzle/` 目录，库里也没有 `__drizzle_migrations` 表，连的一直是开发库。

错的不只是一处。这个约定从 `AGENTS.md` 扩散到了 `README.md` 和架构文档，**三个文件一致地错着**。而一致性恰恰是它没被早点发现的原因——看到三处说法相同，很自然会认为它是被反复确认过的。

现在这条被改写得更完整，把"为什么"和"什么时候必须重新评估"一起写了进去：

> 本项目处于开发期，表结构变动频繁，**刻意不使用迁移机制**——仓库无 `drizzle/` 目录、库中也没有 `__drizzle_migrations` 表。这是有意选择，不是遗漏。
>
> ⚠️ 但从开发库走向生产库之前，必须重新引入正式迁移机制。届时**绝不可对生产库直接 `push`**——它会直接改结构、无版本记录、无回滚路径。

## 八、后台的边界

最后是安全护栏，也是最该提前想清楚的一环：**管理员把自己锁在门外怎么办？**

把角色改错的后果是灾难性的——一旦没有管理员，所有管理能力都失效，而且从界面上无法恢复。

处理方式是在**所有**涉及自身的高危操作上禁用按钮：改自己的角色、封禁自己、模拟自己、删除自己。同时保留一条文档化的恢复路径：直接执行一条 SQL 把自己提回管理员。

后台完成后，`/admin` 是这个站的第一个真正的应用页面。它也验证了架构文档里那个判断——内容层、表现层、身份层互不依赖。这次只碰了身份层与表现层，内容层一行都没动。
