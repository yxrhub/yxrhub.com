前面几篇记的是"做了什么"。这一篇记的是"怎么把它写下来"——因为写这件事本身也做了几个决定，其中一个做错了，而且错得值得单独记一笔。

到这一步，站点已经有一页能看的内容、一套登录、一个后台。但内容只有一页：首页。而开发过程中攒下的判断和坑，一直散在提交记录、临时文档和会话上下文里。

需要一个地方安放它们。这就是 `/blog`。

## 一、日志的 URL 该长什么样

最初的想法是给每篇文章一个不重复的编号，像 `/blog/20261001-a1b2c3d4`。好处很实在：永远不会冲突，不用想短名。

但它有一个更实在的坏处：**这个地址对人是没有意义的**。从它看不出这是什么文章、什么时候写的；想抄给别人的时候只能复制粘贴；搜索引擎拿到它，也不知道该给谁看。

日志和普通文章不一样的地方在于：**日期是它身份的一部分**。一篇六月的日志和一篇十月的日志是两件不同的事，先后顺序本身就是信息。

所以最终的结构是 `/blog/<日期>-<短名>`：

```
/blog/2026-06-24-project-kickoff
/blog/2026-10-01-admin-console
```

扁平一层，肉眼可读，可手抄，顺序自明。

这里有一个细节值得说清楚：**排序键是 frontmatter 里的 `date`，不是文件名。** 上面名字里的日期是给人看的；哪天觉得短名起得不好，改名不影响文章在列表里的位置，也不影响上下篇。**"URL 里写着日期"和"用日期排序"是两件独立的事**——把它们分开，是为了让改名的代价降到零。

## 二、加一篇文章，应该只需要加一个文件

第二个决定是内容怎么存。

最直接的做法是新建一个页面文件，把正文写进去。代价是每加一篇日志都要动代码，而且列表页、上下篇导航都得跟着改。

用的是 Astro 7 的内容层（Content Layer）：一个 `src/content.config.ts` 声明集合和字段约束，正文就是普通 Markdown 文件。

```ts
const blog = defineCollection({
    loader: glob({ pattern: "**/*.md", base: "./src/content/blog" }),
    schema: z.object({
        title: z.string(),
        date: z.coerce.date(),
        summary: z.string(),
        minutes: z.number().int().positive().optional(),
    }),
});
```

**效果是：加一篇日志 = 往 `src/content/blog/` 里放一个 `.md` 文件。** 不用改路由、不用改列表、不用改导航。

字段少是刻意的。日志不是文档，多一个必填字段就多一次"算了不写了"的摩擦。

这里有个容易混的地方：仓库里其实**有两套内容机制**。`src/content/index.md` 是首页正文，走的是原始 Markdown 模块导入，不属于任何集合。所以集合的 `base` 精确指向 `src/content/blog`，没有顺手扩大范围——两套机制各自成立，混在一起才是麻烦。

## 三、同一份排版，不要写两遍

正文样式原本住在 `Welcome.astro` 里，是随首页一起长出来的。

现在第二处地方要显示长文了。可以直接复制一份过去——看起来只是样式而已。**但那样就有了两份真相**：改了一处忘了另一处，两边会慢慢长歪。

所以把 `.prose` 那一整段抽成了 `src/styles/prose.css`，由全局布局引一次，首页和日志共用。

抽取时顺手补齐了首页从没用过的元素：表格、代码块、引用、有序列表、分隔线。**首页用不到不等于日志用不到**——它们之前只是没出现过，不是不需要。

顺带捡到一个作用域的简化。原先在组件里针对注入的 Markdown，样式必须写成 `:global(...)`；换成普通的全局样式表之后，**这些 `:global()` 全都不需要了**。

样式是外抽的，风险就变成"首页会不会被改坏"。所以动手前先抓了一张首页截图作为基线，改完逐项比对：**样式表位置的变动，不该产生任何视觉差异。**

## 四、代码高亮与「没有开关的暗色模式」

这一节的坑很典型：**官方文档给的写法，在本站不成立。**

代码高亮用 Shiki，配了双主题，并关掉默认颜色，让它只输出两套配色的 CSS 变量：

```js
shikiConfig: {
  themes: { light: 'github-light', dark: 'github-dark' },
  defaultColor: false,
}
```

官方示例给出的主题切换方式是给 `<html>` 加一个 `dark` class，然后：

```css
html.dark .astro-code span { color: var(--shiki-dark); }
```

**但本站没有 `html.dark` 这个 class，也不打算有。** 明暗切换走的是 `prefers-color-scheme` 媒体查询，零 JavaScript——这是首页重构时就定下的原则（见[那篇日志](/blog/2026-09-29-homepage-redesign)）。

同一件事于是必须换一种表达：用媒体查询代替 class 选择器。

```css
.prose .astro-code,
.prose .astro-code span {
    color: var(--shiki-light);
    background-color: var(--shiki-light-bg);
}

@media (prefers-color-scheme: dark) {
    .prose .astro-code,
    .prose .astro-code span {
        color: var(--shiki-dark);
        background-color: var(--shiki-dark-bg);
    }
}
```

漏掉这段的后果是：暗色模式下代码块是一整块浅色底。因为 Shiki 已经不写颜色了，而"没人写"等于"没有颜色"。

**教训是：抄配置的时候，要连它假设了什么一起抄。** 官方示例假设了一个 class 开关；配置项本身没错，错的是它默认存在一个本站没有的东西。

## 五、一次自我纠错：我把规则写早了

这是本篇最主要的部分。

日志是中文 Markdown，里面有大量加粗。用浏览器截图复核时，发现有一句的星号**原样显示**了：

```md
**这个思路的问题在于，它把最容易出错的部分留给了自己**。权限校验看起来是一行 if……
```

于是开始找规律。用了一个"加粗后面直接接非标点字符就不解析"的判据扫全文，报出 **16 处**，全部改写，还把它当成红线写进了 `AGENTS.md`。

后来写校验脚本，要顺手，就把 CommonMark 的定界符规则正经推了一遍——推出来的结论是，**把报出来的 16 处逐条过一遍，只有 4 处是真会失败的**。

这时候有两条路：相信自己的推导，或者相信那次扫描。而两边都不该被信。

所以建了一篇探针文章，把各种写法一次性排进去，跑真机看渲染结果：

| 写法 | 结果 |
| --- | --- |
| `**加粗**汉字` | 正常 |
| `前缀。**加粗**后缀` | 正常 |
| `**加粗**，汉字` | 正常 |
| `**加粗。**下一句` | **失败** |

**只有最后一种会失败**：闭合的 `**` 左边是标点、右边又是汉字。而我改掉的那 12 处，本来完全没问题——它们是被一条写错的约定改掉的。

于是回退那 12 处、恢复原文，再把红线、架构文档、校验脚本和沉淀下来的技能一并修正。

**这件事真正值得记的不是"我找到了规律"，而是"一条错的约定比它要防的那个坑更贵"。** 坑本身只影响一篇文章的排版；错的约定会让人去改本来正确的句子，而且改的人照着的是"权威文档"，不会有任何怀疑。

复核手段也换掉了：现在**渲染后搜正文里有没有残留的 `**`**。源文件层面的正则怎么调都会误报，而渲染结果不会说谎。**能验证结果的时候，就不要去验证自己对规则的记忆。**

写完这句才发现，它和前面那篇[排障记](/blog/2026-09-29-vite-cache-incident)是同一条：**先看现象，再看模型。**

## 六、把截图留给这一版

日志里放了截图，理由不只是"好看一点"。

**界面一定会变。** 这一版的首页区块、这一版的文章卡片、这一版的窄屏布局，过几个月大概率就不长这样了。到那时，一篇写着"列表按年分组"的文字，读者只能靠想象；而一张截图能说明当时究竟是什么样子。

所以约定是：**截图记录的是某个版本，不是"这个界面"。** 每张图注都带上截图日期，就是为了让这句话成立——有了日期，"过时"就不再是缺陷，而是它存在的意义。

截图的落地约定：

| 项 | 约定 |
| --- | --- |
| 路径 | `/images/blog/<slug>-<N>.jpg`，`N` 是文章里的阅读顺序 |
| 格式 | 不需要透明的用 JPEG，需要透明才用 PNG。截图基本不透明，所以全走 JPEG |
| 文字 | 文字截图必须 `chromaSubsampling: 4:4:4`；默认的 4:2:0 会让中文细笔画长出彩边 |
| 尺寸 | **原样保留**，既不裁切也不缩放。截图里的留白、区块间距、页面到哪一行结束，本身就是这一版界面的信息 |
| 布局 | `<img>` 上写 `width`/`height`，避免图片加载时正文跳动 |

还有一条是吃过亏才补上的。

最初为了让版面紧凑一点，管线里加过一道自动处理：先按固定像素裁掉底部的开发工具栏，再自动裁掉末尾的空白行。跑出来的图看着挺利落，但很快就发现不对——**每张图都按自己的内容长度截断，同一批截图的取景变得参差不齐**；更糟的是裁掉多少取决于一条阈值规则，规则判错时是**静默地切走真实内容**，而不是报错。

回头看，这里其实被一个假问题带偏了：需要处理的只有"开发工具栏"这一个浮层，而它**根本不该用裁切来对付**。它是开发期产物、不属于页面内容，那就让它在**截图那一刻**不出现（隐藏掉再截），而不是事后从底部赔上一刀。省掉裁切，也就省掉了"该裁多少"这个必然出错的判断。

## 七、日志的边界

最后说说它不该变成什么。

**日志不是变更日志。** 变更日志回答"改了什么"，日志回答"为什么这样改"。所以这里没有"新增 xx 功能"式的条目，只有判断，以及每个判断的代价。

**也不追更新频率。** 什么时候写，取决于有没有值得写的东西，而不是有没有到发布时间。这一篇之所以存在，是因为它包含了一个判断、一个坑，和一次需要被记住的纠错——而不是因为十月一日需要有一篇日志。

---

写这篇时顺手确认了一件事：这套流程（需求 → 计划 → 确认 → 开发 → 验证 → 沉淀）里，"沉淀"那一步的产物，正是能离开当前会话继续存在的东西。日志、架构文档、红线、技能，都是同一个动作的不同形式。

前一篇文章里说过，文档会腐烂、而且会传播错误。这一篇补了另一半：**文档也会把一个人踩过的坑，变成所有人不用再踩的坑——前提是它写对了。**
