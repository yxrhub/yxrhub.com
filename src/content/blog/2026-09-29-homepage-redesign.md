架构文档补完的当天，我接着动了首页。

旧首页严格来说不算难看，只是**空**。一段自我介绍加一串链接，视觉上没有任何结构，也看不出这个站在做什么。更要紧的是它的实现方式：内容与结构混在一起，改一句话要找半天位置。

这次重构有两个目标：让它看起来像个**枢纽**，以及让后续改动变得便宜。

## 一、先定一个原则：内容不能进模板

最直接的重构方式是把新设计直接写进 `.astro` 文件。但那样等于把三个月前的问题原样复制一遍——下次调整文案又要改组件。

所以先定下首页的内容契约：

```markdown
---
projects:
  title: "🌌 正在构建的宇宙 (Projects)"
  intro: "这里是我正在逐步实体化的数字宇宙："
  items:
    - name: "yxrhub.com (本站)"
      emoji: "🌐"
      url: "https://github.com/yxrhub/yxrhub.com"
      positioning: "宇宙的核心锚点。承载我的个人品牌……"
      status: "正在基于 Astro 全栈架构进行重构。"
links:
  title: "🔗 数字世界的我 (Find Me)"
  items:
    - name: "GitHub"
      note: "关注我的开源项目与代码足迹"
      text: "@yxrhub"
      url: "https://github.com/yxrhub"
updated: "最后更新：2026年6月24日"
---

# 你好，我是叶小睿 (Yxr)。

欢迎来到我的数字空间……
```

**一份 Markdown 文件，同时承担两种角色：**

- **正文**是散文——自我介绍、ID 的故事，读起来要连贯，所以用 Markdown 写，编译成 HTML 注入页面；
- **frontmatter** 是结构化数据——项目列表、链接列表，会被渲染成卡片和网格，所以用 YAML 写，由组件遍历。

这个划分的好处很具体：**改文案不用碰组件，改版式不用碰内容。** 加一个社交平台，是在 `links.items` 里加四项；调整卡片样式，是改 `Welcome.astro` 里的 CSS。两件事互不干扰。

代价是 frontmatter 的结构变了，组件里那个手写的类型定义也要跟着改：

```ts
interface DocFrontmatter {
  projects: { title: string; intro: string; items: Project[] };
  links: { title: string; intro: string; items: SiteLink[] };
  updated: string;
}
```

用 `interface` 而不是 `any`，是为了让字段拼错能在编辑器里当场暴露。Markdown 的 frontmatter 在编译期是弱类型的，**类型标注是这里唯一的一道校验**。

## 二、设计令牌：颜色只在一个地方定义

重构的另一半是视觉。第一件事不是写样式，是**把颜色收敛到一处**——`Layout.astro` 的全局样式里：

```css
:root {
  --bg: #fbfbfd;
  --surface: #ffffff;
  --surface-2: #f3f4f9;
  --border: rgba(16, 21, 40, 0.09);
  --text: #101528;
  --text-2: #4a5268;
  --text-3: #8b92a6;
  --accent: #6b4bf0;
  --radius: 14px;
  --shadow: …;
}

@media (prefers-color-scheme: dark) {
  :root {
    --bg: #0c0e18;
    --surface: #151928;
    --text: #eef0f8;
    --accent: #9c8cff;
    …
  }
}
```

配套的是一条硬约束：**组件内禁止硬编码颜色，一律引用变量。**

这条看着像洁癖，实际是深色模式能不能用的唯一保证。一次硬编码不会立刻出问题——它只是在深色模式下变成一个浅色块，而且往往等到上线后才被看见。所以它被写进了红线：**组件里出现十六进制颜色，就是 bug。**

## 三、明暗切换不写一行 JavaScript

主题切换用的是 `prefers-color-scheme`——直接读取操作系统偏好，不提供页面内的开关。

考虑过做手动开关（存 `localStorage`、页面加载前读出来、给 `<html>` 挂 class）。放弃的原因有三个：

**1. 系统偏好已经是用户的答案。** 用户在操作系统里设了深色，就是在表达"我偏好深色"。网页再问一遍，是把已经问过的问题重新问一遍。

**2. 手动方案要解决"闪烁"。** 用 `localStorage` 的写法必须在 `<head>` 里塞一段同步脚本，在首次绘制前把 class 挂上去，否则会先渲染浅色再跳成深色。这段脚本本身就是个容易出错的补丁。

**3. 零脚本意味着零故障点。** 没有 JS，就没有"JS 加载失败所以主题错了"这种可能。

`@media (prefers-color-scheme: dark)` 一行覆盖 `:root` 就够了，浏览器负责剩下的事。

## 四、set:html 的作用域陷阱

重构里踩到的唯一一个真正的坑，出在"用 Markdown 写正文"这件事上。

Astro 的 `<style>` 默认是**作用域样式**：编译时会给选择器加上一个哈希属性，把样式限制在当前组件内。而 Markdown 编译出来的 HTML 是通过 `set:html` 注入的：

```astro
<article class="doc">
  <div class="prose" set:html={body} />
</article>
```

**注入的 HTML 上不会带那个哈希属性。** 于是这样写是没有效果的：

```css
/* ❌ 编译成 .prose[data-astro-cid-xxx] h1 —— 但注入的 h1 不带这个属性 */
.prose h1 {
  font-size: 32px;
}
```

必须显式声明"这部分不受作用域限制"：

```css
/* ✅ */
.prose :global(h1) {
  font-size: 32px;
}
```

更值得记一笔的是它的**编译产物**：

```css
.prose[data-astro-cid-xxx] h1
```

作用域属性挂在了**外层包装** `.prose` 上，而不是内部的 `h1`——因为 `.prose` 是组件自己的元素，`h1` 是注入进来的。也就是说，只要**包装元素**是组件自己写的，`:global()` 里的后代选择器就能正常工作。

这条规则不直观，但一旦理解，就知道 `:global()` 该加在哪一层了。

> **后记**：写这篇日志的时候，这套正文排版已经从 `Welcome.astro` 里抽到了 `src/styles/prose.css`。原因是站点新增了日志模块，同一套排版如果各写一份，加个表格样式就要改两个地方，迟早腐化。抽出来之后，首页正文和文章正文共用同一份规则。

## 五、克制：不新增文案

重构过程中有一个反复出现的冲动——顺手加点东西。

"这里加一句欢迎语会不会更好？""要不要加个『关于我』的标语？""滚动到某处是不是该有个提示？"

最后都否掉了。理由是这个站的定位是**枢纽**，不是内容站：它的职责是清晰地导流，不是留住访客。**每一个新增的句子都在稀释真正重要的那几行。**

所以这次重构定下一条默认克制原则：**不新增对外文案**。需要新增时，先问一句"这个位置真的需要它吗"。

这个原则后来在加日志模块时被用了一次——确实是第一次需要主动往首页加新内容，那就先确认，而不是顺手写上去。

## 六、重构之后

改动本身不算大：一个内容契约、一套设计令牌、一组卡片与网格、一条作用域规则。

但做完之后，改动首页的心理成本明显降低了——文案调整只碰 Markdown，版式调整只碰 CSS 变量和组件样式。**这才是重构真正的产出：不是当前这版页面好不好看，而是下一版改起来有多便宜。**
