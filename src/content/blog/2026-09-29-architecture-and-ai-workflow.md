时间跳到 9 月底，中间隔了两个月没碰这个仓库。

重新打开时，第一个感受不是"忘了怎么写代码"，而是**忘了为什么这么写**。为什么主键要用 UUID v7 而不是自增？为什么中间件里有个 `isPrerendered` 的提前返回？为什么 Dockerfile 里没有 `node_modules` 还能跑起来？

代码能读，意图读不出来。所以这一天的任务不是加功能，是补作业。

## 一、架构文档该写什么

第一反应是"画个图"。但图只描述**现状**——谁调用谁、数据怎么流。而真正丢失的是**决策**：当时有哪些选项、为什么选了这个、否掉了什么。

所以 `docs/ARCHITECTURE.md` 分了五块：

| 章节 | 回答什么问题 |
| --- | --- |
| 技术栈与版本 | 站在什么地基上 |
| 目录结构与模块边界 | 东西放在哪，为什么放这 |
| 数据模型 | 表结构、约束、不可动的部分 |
| 核心数据流 | 一次请求经历了什么 |
| **架构决策记录（ADR）** | **当时为什么这样选，否掉了什么** |

前四块是给人快速上手的，第五块是给**未来的自己**的。

## 二、ADR 的价值在于记录「被否决的方案」

ADR 的格式很简单：编号、决策、理由、代价。

```markdown
| ADR-10 | 全站配色走 CSS 变量 + `prefers-color-scheme`，
          不引入 CSS 框架 | 零新增依赖、体积可控、
          深色模式一处生效 | 组件内硬编码颜色会导致深色模式失效 |
```

看最后两列：**理由**和**代价**。

只写"用了 CSS 变量"，下一个人（或下一个 AI）会说"为什么不装 Tailwind，方便多了"。写上"代价是组件内禁止硬编码颜色"，讨论就落在了正确的位置——不是"要不要换框架"，而是"这条约束值不值"。

**一份好的决策记录，应当让后来者能复现你当时的推理，而不只是接受你的结论。**

## 三、给协作方式定一条流程

补完文档后紧接着的问题是：怎么防止三个月后再次出现同样的局面？

当时的实际情况是——这个项目的开发过程有大量 AI 参与，效率很高，但也暴露了一个模式化的失败：**风险不在"写不出代码"，而在"写得太快"。**

具体表现：

- 一句"帮我加个 X"，直接产出一堆文件，做完才发现方向理解错了；
- 改完能跑，但没人说得清改了哪些文件、验收标准是什么；
- 出了问题只能整体回退，定位不到是哪一步引入的。

这三个问题的共同根源是**跳过了"说清楚"的环节**。所以流程的核心不是加步骤，而是**把"想清楚"变成一个有产出的动作**：

```text
① 需求整理  →  docs/requirements/REQ-*.md
② 制定计划  →  docs/plans/PLAN-*.md
③ 用户确认  →  【强制关卡】
④ 开发实施  →  代码改动
⑤ 验证      →  验收标准逐条对照
⑥ 沉淀      →  文档 / 决策
```

其中两个设计是刻意的：

**需求必须写 Out of Scope。** 只写"要做什么"的需求一定会膨胀——因为任何相关的东西看起来都"顺手可以做"。明确写出"本次不做权限分级、不做审计、不做邮件"，边界才是硬的了。

**计划必须给出至少两个候选方案。** 只有一个方案的"计划"其实是"决定"的伪装。逼着写出 A/B 才能暴露取舍——比如"自建管理 API"和"用现成插件"，不写出来就不会发现自己正在重写最容易出错的那部分。

## 四、为什么「用户确认」是强制关卡

这一条单独说，因为它最容易被跳过——尤其是在流程看起来"很清楚"的时候。

道理很简单：**计划的正确性无法由写计划的人自己保证。** 需求理解偏了，计划会一路顺下来，每一步都自洽，直到做完才发现整体方向错了。这时候返工成本是最大的。

强制关卡的存在，是把"方向确认"和"细节实现"分开：方向错了只损失一份文档，不会损失一堆代码。

配套的还有一条具体规定：**AI 要把计划用自然语言复述一遍，而不是丢一个文件链接。** 因为"我写了计划你没看"和"我讲了一遍你点头了"是两种完全不同的确认强度。

## 五、红线：把踩过的坑变成约束

流程管的是"怎么做事"，但有些教训是**具体的、不可商量的事实**。这类东西单独归到 `AGENTS.md`，叫红线。

比如：

> **`schema/auth.ts` 的列名是 better-auth 的数据契约**，snake_case 不可改。
>
> **`middleware.ts` 的 `isPrerendered` 短路分支不可删。**
>
> **`astro.config.mjs` 的 `ssr.noExternal: true`（生产）不可动**，这是"运行镜像只带 `dist`"的前提。

红线有两条特征，也是它区别于普通文档的地方：

1. **它是被某次事故逼出来的**，不是设计时想出来的；
2. **违反它的代价明显大于遵守它的成本**，所以不需要每次重新权衡。

第 2 点尤其重要——**红线要少。** 如果每件事都是红线，红线就不存在了，只是变成一份没人读的规矩。

## 六、文档是会腐烂的，而且会传播错误

写这套东西的时候有个判断，后来被证明是对的：**文档不只是会过时，它还会把错误固化下来。**

一份没人维护的文档比没有文档更危险——因为读者会信任它。

举个例子。当时我在 `AGENTS.md` 里写下"数据库变更只能走 `drizzle-kit generate`"。但实际情况是：这个项目**刻意不用迁移文件**——仓库里没有 `drizzle/` 目录，库里也没有 `__drizzle_migrations` 表,连的一直是开发库。

我的假设没有被纠正，于是这个错误约定从 `AGENTS.md` 扩散到了 `README.md` 和架构文档，三处一致地错着。**一致性让错误更难被发现。**

这条教训后来变成了流程第⑥阶段的一条规定：**代码改动若使文档失效，必须在同一次变更中更新文档。** 不是"下次一起改"——下次就是三个月后。

## 七、轻量通道

流程如果对所有改动都一视同仁，很快就会被绕过。所以留了一条：

改文案、改样式、修单个函数的 bug —— 可以跳过需求与计划的**文档产出**，但口头说清"改什么、为什么、怎么验证"仍不可省。

同时明确列出**不允许走轻量通道**的范围：认证、中间件、数据库 schema、部署配置、环境变量。理由是这几处的错误不会局部化——改错一个 cookie 属性，全站登录都可能失效。

**流程的可用性取决于它是否给小事留了出口。** 一个"所有改动都要写两份文档"的流程，结局一定是没人遵守。

---

补完这一天的作业后，仓库里多了四份东西：架构文档、决策记录、AI 开发流程、以及一份写给协作者（包括 AI）的 `AGENTS.md`。它们没有增加任何功能，但下一个功能——首页重构——做起来明显不一样了：先有需求，再有计划，改完有验收清单，出问题能定位到是哪一步。
