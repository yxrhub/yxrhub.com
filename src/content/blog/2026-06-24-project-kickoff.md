2026 年 6 月 23 日，我把用了很多年的静态主页从仓库里清掉了。第二天，`pnpm create astro` 生成了一个空项目。

这不是"换个框架再写一遍"。我想要的东西变了：过去那是一个**个人名片**，现在我要的是一个能长期生长、能承载我全部数字产出的**底座**。这篇日志是它的起点——想做什么、不做什么、以及为什么落在现在这套技术栈上。

## 一、旧站为什么必须重做

旧站是一个手写的单页 HTML：内容写死在标签里，没有构建流程，没有数据层。它的三个缺陷都是结构性的，不是靠改几个 CSS 能解决的：

- **内容与表现焊死**。改一句自我介绍，要在几百行标签里找那个 `<p>`。文案调整的成本高到会让人放弃调整。
- **没有可以插入新形态的位置**。将来要加博客、加登录、加后台，没有任何一处是"准备好接东西"的。
- **没有工程约束**。没有构建、没有类型、没有校验，"浏览器能打开"就是唯一的验收标准，因此任何改动都是盲改。

一句话：它是个**成品**，不是个**工程**。

## 二、三条目标

按优先级排，冲突时上面的赢。

**1. 成为枢纽（hub）。** 站名 `yxrhub` 里的 "hub" 不是装饰。GitHub、B 站、YouTube、未来的游戏官网……这些散落的足迹需要一个统一的入口，而不是各挂一串链接。这里要成为那个入口。

**2. 成为可生长的底座。** 我现在说不清三年后会往上放什么。因此架构的第一要求不是"功能够用"，而是**留出插入点**：内容能独立于表现演进，身份层能独立于页面演进，新模块（博客、后台、工具）能加进来而不推翻既有结构。

**3. 工程上说得清楚。** 每一步为什么这样做，要能写成文档、能被未来的自己读懂。这条听起来虚，但它直接决定了下一个决定——见第四节。

## 三、明确不做

**不做什么，比做什么更能说明这个站的定位。**

- 不做博客系统之外的通用 CMS——写作就走"仓库里加一个 Markdown 文件"。
- 不做多用户社区。登录只服务于「我自己」，不开放注册。
- 不做前端框架全家桶。交互只用在真正需要交互的地方，其余交给服务端渲染的静态 HTML。
- 不做过度设计：不引入状态管理库、不引入 CSS 框架、不上微服务。

## 四、技术选型

选型的原则只有一条：**每一项都要能说出"不选它的替代方案会失去什么"。**

| 领域 | 选择 | 不选它的代价 |
| --- | --- | --- |
| 框架 | Astro，Node standalone SSR | 纯静态站做不了登录态；全客户端 SPA 则首屏白屏、SEO 差 |
| 交互 | React 岛屿（按需水合） | 全站水合会把一堆静态内容的 JS 也发到浏览器 |
| 字体/样式 | 原生 CSS 变量 | 引入框架换来的是构建体积与一层抽象 |
| 认证 | better-auth | 手写 session / OAuth / CSRF，是最容易出安全漏洞的地方 |
| 数据 | PostgreSQL + Drizzle ORM | 裸 SQL 没有类型；重量级 ORM 又带来黑盒与迁移耦合 |
| 部署 | Docker + Node 运行时 | 纯静态托管放不下 SSR 与数据库连接 |

其中关于 Astro 的部分值得展开一点：**它的默认值是"静态"，交互是例外。** 这正好匹配上面的目标 2——大部分页面是内容，不需要 JS；少数真正要交互的地方（登录按钮、后台界面）单独挂一个"岛"。默认值选对了，后面就少了很多"防止过度水合"的自觉约束。

关于认证，有一条当时就定下的判断：**身份是最不该自己发明的东西。** session 签名、cookie 属性、OAuth 回调校验，每一环都有大量细节，写错一个就是越权。所以这一层交给成熟库，哪怕它会带来一些约定上的约束。

## 五、架构总览

三层，职责边界清晰：

```
浏览器
  │
  ├─ 内容层  src/content/         Markdown 单一数据源
  │            └─ 编译为静态 HTML
  │
  ├─ 表现层  src/layouts | components | pages
  │            ├─ 静态渲染（默认）
  │            └─ React 岛屿（按需水合）
  │
  └─ 身份层  src/lib/auth.ts  ──►  PostgreSQL
               └─ 会话注入走 middleware
```

关键设计是**内容、表现、身份三者互不依赖**：内容层不知道页面怎么渲染它；表现层通过中间件拿到的 `Astro.locals.user` 决定要不要显示登录入口，但不知道 session 存在哪；身份层只认数据库。

这样带来的直接好处是，后面加博客模块时——只碰内容层与表现层，身份层一行都不用动。

## 六、起步时的目录结构

```text
src/
├── assets/          # 构建期处理的图片资源
├── components/      # 可复用 UI 单元
├── content/         # Markdown 内容源
├── layouts/         # 页面外壳
├── lib/             # 认证、工具函数
├── pages/           # 路由（文件名即路径）
└── middleware.ts    # 全局中间件：会话、访问控制
```

约定：**路由即文件**。要加一个 `/blog`，就在 `src/pages/blog/` 下放一个 `index.astro`，不需要注册任何东西。

## 七、这条日志本身也是架构的一部分

把开发过程写下来，是"工程上说得清楚"这条目标的落地方式。

有些知识只在上下文里成立——为什么当初没用某个方案、那次故障的根因链是什么、哪条约定是被一次事故逼出来的。这些东西散落在提交信息里，一行标题装不下；留在会话记录里，换个上下文就失效。**只写"最终做了什么"的文档，会让人反复踩同一个坑。**

所以我决定把它们写成日志。这一篇是第 1 篇。后面会依次写到身份层、容器化发布、首页重构、一次代价不小的缓存故障，以及后台管理界面。
